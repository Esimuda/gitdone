# Deploy GitDone on Render

GitDone runs as one free web service and one free Postgres database. Accounts sign in with GitLab. The public landing and the GitDone showcase stay readable without an account.

## Blueprint

`render.yaml` at the repository root defines:

- Web service `gitdone`, Node, region Frankfurt, free plan
- Health check `GET /api/health` (`Cache-Control: no-store`)
- Build `npm ci --include=dev && npm run build`
- Start `npm start` (Next.js reads `PORT`)
- Postgres `gitdone-db`, free, Frankfurt, wired to `DATABASE_URL`
- `GITDONE_SESSION_SECRET` and `GITDONE_TOKEN_KEY` generated by Render
- OAuth and showcase values left for you to fill (`sync: false`)

In the Render dashboard: **New → Blueprint**, select this repository, and apply the file. Then set the unsynced variables below and redeploy once they are saved.

## Environment

| Variable | Who sets it | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Blueprint, from Postgres | Accounts, sessions, and connected projects. SQLite is the local fallback when this is unset. |
| `GITDONE_SESSION_SECRET` | Render `generateValue` | Encrypts the httpOnly session cookie. Any string is hashed with SHA-256 before use. |
| `GITDONE_TOKEN_KEY` | Render `generateValue` | Encrypts GitLab tokens at rest. A base64 32-byte key is used as-is. Any other secret, including Render’s generated value, is hashed with SHA-256. |
| `GITLAB_OAUTH_CLIENT_ID` | You | GitLab OAuth application. |
| `GITLAB_OAUTH_CLIENT_SECRET` | You | Confidential client secret. Server only. |
| `GITDONE_PUBLIC_URL` | You | Origin with no trailing slash, for example `https://gitdone.onrender.com`. OAuth redirects use this. |
| `GITLAB_TOKEN` | You | Read-only token for the public GitDone showcase. Not a user session. |
| `GITLAB_PROJECT_ID` | Blueprint | `87419187`, the GitDone project. |
| `GITDONE_ALLOW_TOKEN_PASTE` | Leave unset | `true` only for local development. End users sign in with GitLab. |

Migrations run when the server boots.

## GitLab OAuth application

Create one confidential application on GitLab.com (**User Settings → Applications**, or a group-owned application if you prefer):

| Field | Value |
| --- | --- |
| Name | `GitDone` |
| Redirect URI | `{GITDONE_PUBLIC_URL}/api/auth/callback` |
| Confidential | Yes |
| Scopes | `read_user`, `api` |

Example redirect URI: `https://gitdone.onrender.com/api/auth/callback`.

GitDone uses the authorization code flow with PKCE (`S256`). The session cookie is httpOnly, encrypted with `GITDONE_SESSION_SECRET`, and the OAuth `state` value is single-use. Access tokens are refreshed with the refresh token and stored encrypted. They are never sent to the browser.

## After the first boot

1. Open `GITDONE_PUBLIC_URL` and choose **Sign in with GitLab**.
2. Connect a project you can develop. GitDone opens one install merge request.
3. In GitLab, enable the flow from the AI Catalog, merge that request, and set the CI variable `GITDONE_NOTE_TOKEN`. The checklist on the project ticks each of those from the API.
4. Publish the read-only workspace from project settings if you want `/w/[id]` to be public. It is off until you do.

The landing page and `/mission` keep showing this repository’s showcase from `GITLAB_TOKEN` and `GITLAB_PROJECT_ID`, so someone can browse GitDone without an account.
